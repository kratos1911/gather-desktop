# Embedding request client (not connected)

Developer/server-only code in embedding_client.py prepares bounded batches for
an embeddings HTTP API. It is not bundled into the desktop, reads no environment
variables and performs no work on import. No CLI or default endpoint is enabled.
User deferred account/provider selection on 27 September; live testing remains
deferred, including actual model quality and dollar-cost accounting.

The response shape follows the documented Together embeddings endpoint:
https://docs.together.ai/reference/embeddings (reviewed 27 September 2026).
This is a candidate protocol, not a provider/model selection or availability
claim. The provider's older embeddings overview redirects to deprecations;
verify exact model availability, revision, token limits and pricing before use.

Techniques: **adapter** separates HTTPS from batching/validation; **batching**
reduces request overhead; **preflight validation** checks every input before any
request; **dependency injection** substitutes a fake transport/tokenizer in tests.
Returned indices restore the caller's original order even if a response is shuffled.

Callers supply already-formatted inputs, a pinned model tokenizer including
special tokens, model ID, dimensions, per-input and whole-job token limits,
batch size and request cap. A character/word count is not a production tokenizer.
Only tests use a word-count stub. No silent truncation or automatic retry is
implemented. An error aborts the result, but earlier successful batches can still
have incurred charges; a rerun may charge again. Token/request caps are not a
dollar budget; provider billing limits and job-wide orchestration remain required.

Transport requires an operator-reviewed HTTPS URL and in-memory credential,
refuses redirects, applies a 30-second socket timeout and 4 MiB response bound,
and replaces HTTP/provider exception bodies with fixed errors. Timeout is a
socket-operation limit, not a complete job deadline. Do not accept end-user URLs
or expose this function as an unauthenticated endpoint. No payload/key logging.

Response validation requires the expected model, complete unique indices,
finite nonzero vectors of the expected size, and optional nonnegative usage.
Absent usage stays null rather than zero. Success reports preflight tokens and
provider-reported tokens separately. No unsupported claim of a pinned backend
revision or provider truncation behavior is made from this API response alone.
Consequently the client does not yet stamp a benchmark export as untruncated;
tokenizer/provider verification and export orchestration are later integration.

Tests use mock responses only, including HTTPS error mapping without networking.
Existing synthetic benchmark numbers are not generated by this client.
